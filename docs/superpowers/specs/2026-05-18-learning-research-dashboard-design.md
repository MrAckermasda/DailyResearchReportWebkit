# 学习科研日推网页与周报系统设计

## 1. 目标

为当前“学习与科研日推”项目增加一个本地网页与周报初稿生成流程，满足以下目标：

- 每天快速查看今日重点
- 浏览历史日推归档
- 每周日生成一份 Markdown 周报初稿
- 维护一棵可视化知识树，用于汇总已学内容并管理未来学习方向

系统应直接复用现有 PowerShell 与 Markdown 产物，不引入数据库，不改成复杂 Web 服务。

## 2. 范围

本次设计包含三部分：

- 一个本地网页站点
- 一组用于生成网页数据与周报初稿的 PowerShell 脚本
- 一套与现有日推生成流程兼容的目录结构

本次设计实际覆盖四类能力：

- 首页驾驶舱
- 历史归档浏览
- 周报初稿生成
- 知识树可视化与维护

本次设计不包含：

- 登录与账户系统
- 云同步
- 数据库
- 在线编辑器
- 复杂全文搜索
- Word 周报自动导出

## 3. 用户目标

### 3.1 每日使用

用户每天打开网页后，应在第一屏快速知道：

- 当前有多少逾期任务
- 今天有哪些必须完成的任务
- 接下来三天有哪些紧迫任务
- 当天日推里有哪些论文、视频、开源项目更新

### 3.2 历史浏览

用户应能按日期查看历史日推，并保留原始 Markdown 的信息结构。

### 3.3 周报初稿

每周日应生成一份 Markdown 周报初稿，供用户后续手工润色为正式周报。周报内容应覆盖：

- 本周学习科研进展与收获
- 本周项目进展与收获
- 下周学习科研计划
- 下周项目计划

### 3.4 知识树

用户应能维护一棵知识树，同时支持：

- 汇总已经学过的知识板块
- 标记当前正在推进的内容
- 记录未来想学的方向

知识树应采用“自动生成底稿 + 手工调整”的混合模式，而不是完全手工维护，也不是完全自动推断。

## 4. 信息架构

系统分为四个页面：

### 4.1 首页

首页采用“今日驾驶舱”方向。

首页结构：

- 顶部状态栏：日期、星期、今日摘要
- 核心任务区：逾期未完成、今日截止、未来 3 天
- 本周摘要区：本周学习科研 / 项目概览
- 当日日推摘要区：DDL、arXiv、视频、开源项目
- 最近归档入口：最近几天的历史日推

首页优先级是“先告诉用户今天该做什么”，不是完整阅读所有历史内容。

### 4.2 归档页

归档页结构：

- 左侧日期列表，按新到旧排列
- 右侧显示当天完整日推内容
- 支持基础筛选，第一版只做简单模块筛选，不做全文搜索

归档页保留原始 Markdown 的章节结构，避免重新设计内容模型。

### 4.3 周报页

周报页结构：

- 周报列表，按周倒序显示
- 单篇周报内容渲染区
- 原始 Markdown 入口

周报页的职责是查看和管理周报初稿，不负责最终排版成 Word 成品。

### 4.4 知识树页

知识树页采用“三栏结构”：

- 左侧：筛选、统计、主线过滤
- 中间：主树展示区
- 右侧：节点详情、证据来源、编辑操作

知识树不是纯展示图，而是学习驾驶舱中的长期结构化面板。

推荐结构是“主树 + 关联引用”：

- 主结构保持树形，便于按学习主线浏览
- 少量跨领域知识点允许通过“关联到”进行横向连接

知识树顶层按主线组织，第一版默认包括：

- 数学地基
- FOC 电机控制
- SLAM
- 复合翼项目

第二层及更细节点按模块拆分，并为每个节点维护状态：

- 想学
- 在学
- 已学

## 5. 数据来源

### 5.1 日推内容

来源于当前目录下每天生成的日推 Markdown 文件，命名模式优先识别：

- `YYYY.MM.DD 学习与科研日推.md`
- 兼容其他已有日推命名

### 5.2 DDL 数据

来源于项目中的 `DDL清单.md`。

### 5.3 项目进展素材

来源于桌面 `复合翼` 目录中最近一周发生变化的文件。

第一版只使用文件变更时间、文件名等弱结构化信息作为项目进展线索，不假定项目目录内已有稳定日志格式。

### 5.4 周报结构参考

来源于桌面 `周报` 目录中的现有周报文档，作为章节结构和语气参考。

### 5.5 配置

继续复用现有 `research_digest_config.psd1` 的配置思路；如需要新增网页或周报配置，沿用 PowerShell data file 风格。

### 5.6 知识树来源

知识树底稿来源于以下材料：

- `DDL清单.md`
- 每日日推
- 每周周报

知识树还需要一个单独的手工维护文件，用于保存用户编辑结果与自动数据无法稳定推断的信息。

## 6. 系统方案

推荐采用“PowerShell + 本地网页”一体化方案。

分工如下：

- PowerShell：负责扫描 Markdown、整理索引、生成周报初稿
- PowerShell：负责生成知识树自动底稿与合并后的知识树数据
- 本地网页：负责展示首页、归档页、周报页、知识树页，并提供轻量编辑入口

这样做的原因：

- 复用当前已有的 `generate_research_digest.ps1`
- 与现有本地工作流兼容
- 实现成本低于完整后端服务
- 后续仍可继续扩展

## 7. 数据流

### 7.1 首页数据流

1. 脚本扫描全部日推 Markdown
2. 识别最新一天的日推作为默认首页内容
3. 提取首页需要的摘要数据：
   - 逾期任务
   - 今日截止
   - 未来 3 天
   - 当日日推的论文 / 视频 / 开源项目摘要
4. 输出网页使用的数据文件
5. 网页加载该数据并渲染首页

### 7.2 归档数据流

1. 脚本扫描历史日推文件
2. 为每篇日推提取日期、标题、摘要与原文内容
3. 生成归档索引
4. 网页按归档索引渲染日期列表与正文视图

### 7.3 周报数据流

1. 每周日运行周报脚本
2. 脚本汇总最近 7 天日推
3. 同时读取最近 7 天的 DDL 状态与 `复合翼` 目录文件变化
4. 生成一份 Markdown 周报初稿
5. 保存到项目内周报目录
6. 网页周报页渲染该初稿

### 7.4 知识树数据流

1. 脚本扫描 `DDL清单.md`、历史日推、周报初稿
2. 提取知识主题、任务名称、阶段线索、完成线索
3. 按主线归类到知识树主结构
4. 为节点生成默认状态：
   - 只出现在未来计划中的内容，默认 `想学`
   - 最近持续推进但未形成完成结论的内容，默认 `在学`
   - 在周报或记录中明确体现完成、总结、实战落地的内容，才进入 `已学`
5. 读取用户手工维护文件
6. 将自动底稿与手工覆盖结果合并
7. 输出网页使用的最终知识树数据
8. 网页渲染知识树，并支持轻量编辑

## 8. 周报生成规则

### 8.1 输出形式

周报初稿输出为 Markdown。

### 8.2 输出结构

固定结构如下：

1. 本周进展与收获
2. 学习科研进展与收获
3. 项目进展与收获
4. 下周计划
5. 学习科研计划
6. 项目计划

实际书写时可保持与现有周报语义一致，例如：

- 一、本周进展与收获
- （一）学习科研进展与收获
- （二）项目进展与收获
- 二、下周计划
- （一）学习科研计划
- （二）项目计划

### 8.3 学习科研内容提取

学习科研部分主要基于最近 7 天日推内容提取：

- 出现的学习主题
- 已完成或推进的学习任务
- 持续多日出现的重点方向
- DDL 中接近截止或已跨周的事项

第一版应以提纲式、概括式语言生成，不伪造细节。

### 8.4 项目内容提取

项目部分主要基于 `复合翼` 目录中最近 7 天更新的文件推断线索。

如果项目目录本周素材不足，则明确输出类似语义：

- 本周项目自动汇总素材不足，建议人工补充具体飞行、调参、测试或部署进展。

系统不得凭空编造项目进展。

### 8.5 下周计划生成

下周计划来源于：

- DDL 中未来一周的未完成事项
- 学习主线的连续任务
- 项目目录相关的待推进方向

若项目计划无法从现有素材可靠推断，应输出保守计划草案，而不是具体未证实结论。

## 9. 知识树生成与编辑规则

### 9.1 结构规则

知识树采用“主树 + 关联引用”模式。

- 每个节点必须有一个主父节点
- 允许节点附带少量“关联到”引用，用于表达跨主线联系

例如：

- `卡尔曼滤波` 可主挂在 `SLAM`
- 同时关联到控制或状态估计相关分支

### 9.2 自动生成底稿

自动脚本负责生成知识树底稿，而不是最终唯一版本。

自动底稿主要完成：

- 从日推、DDL、周报中提取候选知识点
- 按预设主线归类
- 为节点提供默认状态
- 给出来源证据

### 9.3 手工覆盖

用户可手工维护以下内容：

- 新增节点
- 修改节点名称
- 修改节点状态
- 调整父节点
- 增加备注
- 增加或修改“关联到”引用

手工维护结果优先于自动生成结果，后续自动更新不得覆盖用户手工修改。

### 9.4 节点字段

第一版每个知识树节点建议至少包含：

- 唯一标识
- 名称
- 主父节点
- 状态
- 简短说明
- 来源证据列表
- 关联引用列表
- 最近更新时间
- 是否为手工创建

### 9.5 节点状态判定

状态只有三种：

- `想学`
- `在学`
- `已学`

判定原则：

- 只有未来计划或目标项，没有明确推进证据的，归为 `想学`
- 有持续学习、拆分任务、近期跟进，但未完成总结的，归为 `在学`
- 有周报总结、专题整理、实战完成或阶段性总结依据的，归为 `已学`

系统不应仅因某一知识点在某一天出现一次，就自动判定为 `已学`。

## 10. 目录建议

建议在现有项目中增加以下目录：

- `web/`
  - 网页资源
- `data/`
  - 网页索引或中间数据
- `weekly-reports/`
  - 生成的 Markdown 周报初稿
- `knowledge-tree/`
  - 自动底稿、手工覆盖文件、合并后的知识树数据
- `docs/superpowers/specs/`
  - 设计与计划文档

若实现阶段认为更适合，也可以将中间数据放入更明确的目录名，但必须保持网页、脚本、生成物职责分离。

## 11. 页面交互原则

### 11.1 首页

- 第一屏必须能快速扫读
- 优先展示“今天要处理什么”
- 不把完整长文直接堆到第一屏

### 11.2 归档页

- 切换日期应直接
- 阅读正文应稳定
- 结构上更像知识日志浏览器，而不是博客首页

### 11.3 周报页

- 先保证能查看与复制初稿
- 不追求复杂编辑体验
- 每周一篇，按周聚合

### 11.4 知识树页

- 左侧用于筛选主线和状态，并展示节点数量统计
- 中间展示主树，优先保证层级可读性
- 右侧展示节点详情、来源证据、关联链接和轻量编辑入口
- 第一版不做复杂图谱拖拽，不做自由布局

### 11.5 页面联动

知识树需要与其他页面联动：

- 首页展示“当前在学重点”与“最近新增已学节点”
- 周报可引用本周知识树状态变化
- 归档页支持从知识节点跳到相关日推或 DDL 证据

页面联动的核心目标是让知识树成为内容索引，而不是孤立页面。

## 12. 错误处理与边界

### 12.1 缺少外部更新

若某天未抓到 arXiv、视频或开源项目，网页仍应正常渲染，不因某个板块为空而整体失败。

### 12.2 日推命名不一致

脚本应优先识别标准命名，但对已有历史文件提供兼容策略。

### 12.3 项目素材不足

若 `复合翼` 目录在某周缺少足够可推断信息，项目周报部分必须显示“素材不足”提示，而不是编造正文。

### 12.4 周报不是最终成品

周报功能目标是生成“可编辑初稿”，不是自动产出最终可直接上交的正式周报。

### 12.5 知识树自动提取不可靠

若某个知识点无法被可靠归类或判定状态，应保守处理：

- 不强行归为 `已学`
- 可进入候选节点或 `想学 / 在学` 的较保守状态
- 允许后续人工修正

### 12.6 手工修改保护

任何自动生成流程都不得覆盖用户手工维护的知识树字段。

## 13. 验证要求

完成实现后至少验证：

1. 最新日推能正确显示在首页
2. 历史 4 至 10 篇日推能正常切换与渲染
3. 周报脚本能手动生成一份结构正确的 Markdown 初稿
4. `复合翼` 目录素材不足时不会报错
5. 任一日推缺失某个内容板块时页面仍可打开
6. 知识树能从现有材料生成基础主结构
7. 用户手工修改知识树后，再次生成时不会丢失手工内容
8. 知识树节点能跳转到相关日推、DDL 或周报证据
9. 首页能正确展示知识树中的“在学重点”摘要

## 14. 实施边界

第一版重点是把现有内容稳定变成可用工具，不做过度工程化。实现时如遇到以下情况，应坚持收缩范围：

- 用静态文件即可解决的问题，不引入后端服务
- 用 PowerShell 可完成的数据整理，不引入数据库
- 用简单筛选可满足的归档需求，不引入全文搜索
- 用轻量表单可完成的知识树编辑，不引入复杂在线编辑器或图谱引擎

## 15. 未决事项

当前没有功能级未决事项。

唯一已知环境限制是：当前目录不是 git 仓库，因此无法按标准流程提交该设计文档到 git 历史；设计文件仍已落盘，可继续作为后续实现依据。
